# DSH APP — brand plugin suite

The suite is seventeen dsh plugins that layer on top of upstream dsh **without
forking it**. This is what keeps the desktop app updateable: when upstream dsh
releases a new version, the shell swaps the kernel and these plugins keep
working.

| `plugin-rewind` | dual | message recall + file revert: `/rewind <n>` cuts the model-visible surface back to before a chosen user message through the kernel's own surface-replacement mechanism (`session.append('user/message', …, { surfaceOp: { op: 'replace', … }, sourceEventSeqs: … })` with an empty-content placeholder carrying this plugin's source kind; `system/message` is NOT usable here — the persistence validator requires a system message to match the currently open turn/step and a recall runs while the agent is idle, so that shape writes fine and then makes the log unloadable), hides the affected turns in the chat UI via `data-chat-turn`, and returns the recalled text to the composer through `inputActions.setDraft`. The composer face is read from the MATERIALIZED `uiSession` binding (`uiSession.bindingSource`), never from `sessions.binding(id)` — the raw binding carries no props, and reading `props.inputActions` off it fails silently. Entry points: a hover icon under each user message (a `priority: -1` wrapper around the built-in `user` chat-node renderer — safe only because that renderer calls `renderSlot` zero times) and the `/rewind` command (bare = picker, `/rewind <n>` = direct). A typed `/rewind` is observed through the session's append event feed so both entry points prefill alike. A QUARANTINE MANAGER tab in the maintenance settings section lists every displaced file with its origin path and reason (replaced / created), and discards items individually or a whole session to reclaim disk — per-item confirmed, because the safety copy is the only copy. It reads two host routes (GET /api/plugins/dsh-app/plugin-rewind/quarantine and POST …/quarantine/purge) that take session and slot NAMES, never paths: the handler derives the root from $DSH_HOME and refuses a segment holding .., a separator, a drive prefix or a NUL, so a purge cannot leave the quarantine. A CONFIRMATION STEP: clicking the icon asks the host what a recall WOULD do (`/rewind plan <n>`, a separate verb that cannot change anything) and shows a modal listing every file with its action (restore / move away), an expandable before/after diff, and an explicit count of what cannot be restored; the recall runs only on confirm. TWO SCOPES, chosen in that dialog: `withFiles` (the ordinary recall) and `conversationOnly` — `/rewind conversation <n>` — which cuts the messages and leaves every file alone, the case where the file work was right and only the message was wrong. The scope travels as a VERB rather than a flag, so what the dialog chose and what the command does cannot drift through a stringly-typed option; the file revert is skipped by participant ID (every other participant still reconciles, because the turn is off the surface either way) and the recorder's before-images plus the range's snapshots are KEPT, since dropping them would make those files permanently unrestorable. The skipped revert reports `skipped: true` rather than `coverage: 'none'`, so a chosen outcome is never rendered as a failure. FILE REVERT, from TWO sources. (1) The two pre-write waterfalls (`fs/write-intent`, `fs/edit-intent`) are hooked with `{ prepend: true }` and MUST forward `next()` — the kernel's own `fs-observation-policy` listener never forwards, so a normally-registered listener would never run, silently. They give an exact before-image for `write` / `edit` / `str_replace_editor` (22.9% of measured tool calls) and are the only source that sees a write outside the workspace. (2) A bounded workspace snapshot is taken at the TURN BOUNDARY (`session/event` with `turn/start`) and, as a fallback for a boundary walk that failed, before a turn's first tool that could write (the `tools/pre-execute` gate, forwarded and never failed) — the boundary is what makes a recall return the tree as it was when the message was SENT, rather than as it was at the model's first write, and the claim is released on failure so the tool gate can still take it — covering everything the waterfalls cannot see — a shell command, a script the model ran, an office renderer, a subagent's edits (31.4% of measured tool calls) — and stored content-addressed under `$DSH_HOME/storages/dsh-app-plugin-rewind/{trees,blobs}` so an unchanged file costs one hash per turn and no bytes. A path the snapshot covers is restored from it; everywhere else the recorder's before-image wins. The walk skips dependency/VCS/cache directories and is bounded by file count, total bytes, per-file bytes, a deadline and the tool call's abort signal; the store itself is trimmed by per-session turn count, manifest age and total blob bytes. An INCOMPLETE snapshot never decides that a file was created (that judgement moves a user's file out of the workspace), a file the walk saw but could not copy is reported instead of treated as absent, and a linked subtree marks the snapshot partial rather than passing as a clean tree; the recall reports any shortfall instead. `coverage: full | partial | none` rides the result and the confirmation dialog: a range that ran a shell command with no snapshot to fall back on is reported as `none` WITH the tool names, never as a silent success. A restore is byte-exact, so a generated PNG comes back as the PNG it was. NOTHING IS DELETED — displaced content moves into `$DSH_HOME/storages/dsh-app-plugin-rewind/quarantine/`, so the recall itself stays reversible. Only this plugin's own replacements hide turns, and only the FIRST prompt of a turn is a recall point (a steering message sharing the prompt shape is not). A recall always cuts at a turn head and is refused while a turn is running, with the reason shown beside the message; the log is append-only. THE RECALLABLE RANGE STOPS AT THE NEWEST COMPACTION: a compaction checkpoint (`user/message` with source kind `compact-checkpoint`) is not a recall point but it DOES bound the list, so an ordinal past the end answers a dedicated boundary reason, the bare listing and the picker say the same thing, and the confirmation dialog repeats it. A PARTICIPANT REGISTRY, published as `dsh-app-rewind-participants`, lets other suite plugins reconcile their own state after a recall; the file revert is its first participant, so the seam is exercised by behaviour users already depend on, and one participant failing is logged without failing the recall or the participants after it |
| `plugin-effort` | client | reasoning-effort track on the **official model menu's 推理等级 row**. That menu contributes no slot of its own, so the browser half injects ONE container beside the row and turns that row into a capsule (geometry, ring and the level's own colour written as inline styles, every one of them snapshotted before the first write and restored on unmount); the SAME level colour is written onto the composer capsule's own level text — the kernel's `… Max` beside the model name, marked `data-dshAppEffort` and weighted by this plugin's stylesheet, never retyped — so the two readings of one level cannot drift apart. The row is identified from the kernel's OWN dictionary (`ctx.locale.bind('model')('menu.effort')`, which follows the active locale) plus a structural check, and the composer's level span by the trigger's child shape, never by a hashed class; when a shape does not match it writes nothing, because a missing track costs nothing and a track on the wrong row is a wrong control. Levels come from the current model's own advertised list and a position is resolved **by id, never by index** — an id the list does not carry falls back to the model's default and then reports itself as unknown rather than being drawn at the left end. The transient values (drag draft, pending commit, error) are keyed by `provider/model/level-ids`, so a model switch drops them instead of reusing an index that meant something else. Growing the card re-triggers the official menu's own placement (a window resize is the only signal its effect listens for), which is what keeps it from overlapping the composer. The value is written through `ctx.modelDirectories` — the same per-session directory the official seat and `/model` popup read — so all three surfaces stay one state |
| `plugin-workbench` | client | the workbench hub: ONE row in the sidebar's global-panel list (`sidebar.panellist`, order `-1`, so it sorts above the kernel's own 插件 and 自动化任务) opening ONE full-page container (`main`, key `workbench`) that domain workbenches join by registering a card into either of two root-scoped seats — `workbench.item` (the card grid) and `workbench.view` (a domain's own page). A card enters its domain one of two ways: a panel view rendered inside the container, or a workspace entry that opens a folder as a workspace and returns to the conversation (`src/client/entry.ts`). The container owns the seat, the page and the slots; a domain owns its own behaviour. The grid currently holds no domain card and no panel page — a domain appears by registering one, never by a change here; `docs/plans/workbench-hub.md` carries the container's design, its seats and its probe |

## Integration into the kernel runtime

The runtime artifact build (scripts/build-runtime.mjs) adds the suite via
`file:` references into the runtime profile's package.json, so a published
kernel contains dsh + the suite in one immutable directory. Once the suite is
published to npm, switch those references to version ranges.

The loader overlay (`dsh-app.patch.yml`) is copied next to the main bundle at
build time and read at server start. The desktop host takes no `--patch` and does
not read the home layer, so the rows reach the profile as a **bundle layer** on
the web line — the profile declares `@dsh-app/suite-layer`, whose own
`cordis.patch.yml` carries them — and only the frames line (host
`< 0.1.6-alpha.2`) still writes the profile's own `cordis.patch.yml`.
