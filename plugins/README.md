# DSH APP — brand plugin suite

The suite is nineteen dsh plugins that layer on top of upstream dsh **without
forking it**. This is what keeps the desktop app updateable: when upstream dsh
releases a new version, the shell swaps the kernel and these plugins keep
working.

## The archive plugin's trash on disk

`plugin-archives` never unlinks a session's log directory. `/delete` MOVES it into
the plugin's own trash under the harness home, which is why a deletion is undoable
and why only `/purge` (or the retention sweep) frees bytes:

```
$DSH_HOME/storages/dsh-app-plugin-archives/
  trash/
    <trashId>/                      <epochMillis>-<uuid first 8>
      metadata.json                 identity and labels ONLY: version, state,
                                    deletedAt, and one entry per member with
                                    sessionId, title, originalPath, payload, sizeBytes
      payload/<n>/                  ONE moved member, exactly as it sat under the
                                    sessions root (session logs + sidecars); <n> is
                                    the member's index in metadata.json
  settings.json                     { version: 1, retentionDays, sweepOnStartup }
$DSH_HOME/logs/dsh-app-plugin-archives.log     one JSON line per action, rolls to .1
```

`metadata.json` is written TWICE — `state: "moving"` before the first rename,
`state: "ready"` after every rename is verified — so a crash can never leave a
payload nothing can name; a `<trashId>.purging` directory is a deletion that did not
finish and is listed by the panel so it can be retried.

**Recovering a session by hand** (the fallback if the plugin is rolled back, or if
the panel cannot reach the row): read `metadata.json`, take the member's
`originalPath`, and move `payload/<n>` back to it. The disk is the only truth — the
metadata names things and never decides anything, so a hand move is exactly what the
plugin's own restore does:

```
mv "$DSH_HOME/storages/dsh-app-plugin-archives/trash/<trashId>/payload/0" \
   "<originalPath from metadata.json>"
```

Moving a whole `payload/` back into a project directory restores a batch; leaving an
entry alone is harmless (it is just directory tree the plugin no longer references),
which is what makes a code rollback safe. A session restored this way has no archive
record, so it returns visible in the sidebar instead of archived — archive it again
from the UI if it should stay hidden.

## Integration into the kernel runtime

The runtime artifact build (scripts/build-runtime.mjs) adds the suite via
`file:` references into the runtime profile's package.json, so a published
kernel contains dsh + the suite in one immutable directory. Once the suite is
published to npm, switch those references to version ranges.

The loader overlay (`dsh-app.patch.yml`) is copied next to the main bundle at
build time and read at server start. The desktop host takes no `--patch` and does
not read the home layer, so the rows reach the profile as a **bundle layer** on
the web line — the profile declares `@dsh-app/suite-layer`, whose own
`cordis.patch.yml` carries them — and only the frames line (host
`< 0.1.6-alpha.2`) still writes the profile's own `cordis.patch.yml`.
