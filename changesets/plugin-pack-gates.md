打包链与 PR 门禁上新增三条插件门禁：每个插件在构建与打包前先跑自己的 `npm run typecheck`（esbuild 不做类型检查，客户端半边引用到已删除的导出，原本只有在用户拖动时才在渲染进程抛 `ReferenceError`），再校验构建产物按插件自己的声明确实存在且非空（`files` 里指向 `lib` 的条目加上 `main`/`exports` 落在 `lib/` 下的入口；npm 对缺失的 `files` 目录是静默略过，构建什么都不写时全线绿灯），最后拒绝 `lib/` 比该插件任何输入都旧的产物（`lib/` 被 gitignore，dev 跑的和打包读的可能是两个时刻的产物）；三处执行点执行 `scripts/lib/plugin-gates.mjs` 里的同一份判定：`scripts/build-runtime.mjs` 自己的 per-plugin 构建循环（构建完立刻校验产物）与 `packPlugin`（打包前校验陈旧）、发布流程的预构建循环、以及 `ci.yml` 的 `gate` 作业（PR 阶段；干净检出上陈旧那一半按构造通过，能咬住的是类型门禁与产物存在性）——所以本地 `runtime:build` 在构建后就会拒绝没有产物的插件。
Three checks now stand on every path that builds or packs a suite plugin, all decided once in `scripts/lib/plugin-gates.mjs`: each plugin runs its own `npm run typecheck` before it is built (esbuild does not type check, so a client half calling an export that was removed failed only in the renderer, on the user's first drag); the build's declared outputs must exist and be non-empty (the `files` entries naming `lib`, plus `main` and the `exports` targets under `lib/` — npm omits a missing `files` directory from the tarball silently, so a build that writes nothing used to be green everywhere); and a `lib/` older than any file that feeds it is refused rather than packed (`lib/` is gitignored, so the tree a developer runs and the tree a pack reads can come from two different moments). All three call sites — `scripts/build-runtime.mjs` (which runs every check itself: types and outputs in its per-plugin loop, freshness before it packs), the release workflow's pre-build loop, and `ci.yml`'s `gate` job, where a broken plugin now stops before a merge — run the same verdicts, so a local `runtime:build` refuses a plugin whose build produced nothing; on a clean checkout the freshness check passes by construction, so the type gate and the presence check are the halves CI proves.
