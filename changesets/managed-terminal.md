托盘「打开终端（dsh 命令行）」现在经由**系统默认终端应用**打开：Windows 上用 `start` 新建控制台（默认终端是 Windows Terminal 时会作为新标签/新窗口出现），不再由本进程直接启动——那条路径下交互式 shell 的 stdin 是 NUL，读到 EOF 立刻退出，窗口从头到尾不会出现而托盘仍报告成功。控制台一律是 `cmd.exe`，用户偏好的 shell（`SHELL` → `ComSpec` → PowerShell → cmd）改由批处理最后一行接手（PowerShell 以 `-NoLogo -NoExit` 进入），拿不到就停在 cmd 提示符；`cmd.exe` 解析不到时明确报错，不再静默换成别的程序。终端环境不变：`PATH` 最前面是本机的私有 shim 目录（`dsh`/`node`），`pnpm` 指向当前运行时的内置版本，并带上这个应用真正启动的 `DSH_HOME` 与 `DSH_APP_PROFILE`——市场里装/卸/升级失败后要手工改 `cordis.patch.yml` 时，可以直接在该终端里跑 `dsh plugin --profile dsh-app add <包名>`（`--profile` 是内核 `plugin` 子命令的必填项，CLI 不读 `DSH_APP_PROFILE`）；`chcp 65001` 保留，路径含中文不乱码。不改系统 `PATH`、不写用户的 shell 配置、不动内核源码。本机还没有可用内核（`kernelCliPath()` 为空，或它指的文件不在）时，这一项**置灰**（`enabled: false`），不再让人点进一句"本机还没有可用的内核"；置灰与"点了会不会成功"走同一个判据（`kernelCliUsable()`），菜单在每次重建时重算，内核激活后即恢复可点。其余失败（写不进 shim、没有可用控制台、解析不到 Node）仍照旧弹出提示。
The tray's "Open terminal (dsh CLI)" now opens through the **system default terminal application**: on Windows the console is created by `start` (with Windows Terminal as the default application it appears as a new tab or window), instead of being spawned by this process — that path gave the interactive shell NUL for stdin, which reads as EOF and exits at once, so no window ever appeared while the tray still reported success. The console is always `cmd.exe`, and the user's shell preference (`SHELL` → `ComSpec` → PowerShell → cmd) is now the batch file's last line (`-NoLogo -NoExit` for PowerShell), ending at the cmd prompt when nothing resolves; a `cmd.exe` that cannot be resolved is a reported failure rather than a quiet substitute. Everything the terminal carries is unchanged: this machine's private shim directory first on `PATH` (`dsh`/`node`), `pnpm` pointed at the running runtime's bundled copy, and the `DSH_HOME`/`DSH_APP_PROFILE` this app actually booted — so when a market install, removal or upgrade fails and the advice is to edit the profile's `cordis.patch.yml` by hand, `dsh plugin --profile dsh-app add <package>` can simply be typed there (`--profile` is a required option of the kernel's `plugin` subcommand; the CLI does not read `DSH_APP_PROFILE`). `chcp 65001` is kept, so paths with non-ASCII characters are not mangled. The system `PATH` is untouched, no shell configuration file is written, and no kernel source is modified. When this machine has no usable kernel yet (an empty `kernelCliPath()`, or a path whose file is not there) the item is now **greyed out** (`enabled: false`) instead of being clickable and answering with a "no usable kernel yet" notice; being greyed and "would the click have worked" are the same predicate (`kernelCliUsable()`), recomputed on every menu rebuild, so the item becomes clickable again as soon as a kernel is active. The other failures (an unwritable shim, no console, no resolvable Node) keep their notice.
